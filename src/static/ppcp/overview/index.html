1. What we've built

SpreedlyPPCP is a new class in Spreedly's Checkout Web SDK that embeds PayPal's JS SDK v6 inside Spreedly Checkout. It renders PayPal's branded buttons — PayPal, Pay Later, Venmo (and optionally PayPal Credit) — and drives the full v6 payment-session lifecycle.

It ships in both of Spreedly's browser bundles (hosted-fields and express-checkout) as a window global, so any merchant already using Spreedly Checkout gets PPCP without a second integration.

Design principle: the SDK never calls a payment API and never holds payment credentials. It orchestrates PayPal's browser SDK and hands the outcome to the merchant. Every money-moving call is made by the merchant's backend.

3. Step-by-step: a one-time checkout

Scenario: a $299.99 order. The buyer picks PayPal, Pay Later, or Venmo.

1The merchant constructs the SDK

const ppcp = new SpreedlyPPCP({
  clientId: 'YOUR_PAYPAL_CLIENT_ID',   // static, browser-safe
  currencyCode: 'USD',
  amount: '299.99',                    // required for Pay Later eligibility
  countryCode: 'US',
  paymentElements: {
    paypal:   'paypal-button-container',
    payLater: 'paylater-button-container',
    venmo:    'venmo-button-container',
  },
  createOrder:     () => /* merchant backend → order id */,
  onPaymentResult: (result) => { /* merchant handles the outcome */ },
});

const { rendered, error } = await ppcp.mount();

2mount() initialises PayPal

paypal.createInstance({
  clientId,
  components: ['paypal-payments', 'venmo-payments'],   // derived from requested buttons
  pageType: 'checkout',
  partnerAttributionId: 'Spreedly_PCP',                // BN attribution
  locale,
})

components is computed from which buttons the merchant asked for, so we only load what's needed.

3Eligibility

instance.findEligibleMethods({
  currencyCode: 'USD',
  countryCode:  'US',
  amount:       '299.99',    // ← decisive for Pay Later
})

Each requested button is then gated on isEligible(...). For this buyer at $299.99, PayPal returns Pay Later as eligible (Pay in 4 and Pay Monthly both qualify). At $25 it would not.

4Sessions and button elements

Per eligible button, the SDK creates the matching session and inserts the web component:

ButtonSession factoryElement
PayPalcreatePayPalOneTimePaymentSession<paypal-button>
Pay LatercreatePayLaterOneTimePaymentSession<paypal-pay-later-button>
VenmocreateVenmoOneTimePaymentSession<venmo-button>
PayPal CreditcreatePayPalCreditOneTimePaymentSession<paypal-credit-button>

Pay Later and Credit additionally receive productCode / countryCode from eligibility.getDetails(...).

mount() returns { rendered: { paypal: true, payLater: true, venmo: true } } so the merchant can adjust their layout.

5The buyer clicks

const orderPromise = createOrder();                 // NOT awaited
session.start({ presentationMode }, orderPromise);

The order promise is passed unresolved. Awaiting it first would consume the click's transient activation and the browser would block the popup — passing the pending promise lets PayPal open the approval surface immediately while the order is created in parallel.

6Approval

The buyer approves in PayPal's UI. onApprove fires with the order id.

7The SDK reports a normalised result

{
  state: 'Successful',
  payment_method: { payment_method_type: 'paypal' | 'venmo' | 'paylater' | 'paypal_credit' },
  orderId: '5O190127TN364715T'
}

Cancellation and failure map to the same shape — state: 'Cancelled' / 'Failed', the latter carrying PayPal's stable code (e.g. ERR_*) alongside the message, so merchants can branch on the reason rather than parse text.

8The merchant captures

The merchant's backend captures the order. The SDK is not involved — its job ends at reporting the approval.

4. Vaulting and recurring

flow: 'vault' switches the SDK to the save-payment path:

new SpreedlyPPCP({
  flow: 'vault',
  createVaultSetupToken: () => /* merchant backend → setup token */,
  paymentElements: { paypal: 'save-button' },   // PayPal only
  ...
})
  • Uses createPayPalSavePaymentSession
  • Eligibility switches to paymentFlow: 'VAULT_WITHOUT_PAYMENT'
  • The result carries vaultSetupToken, which the merchant exchanges server-side for a payment token

Later charges (one-click with the buyer present, or merchant-initiated recurring) are backend-only — the SDK plays no part.

5. Two delivery models

The SDK is deliberately backend-agnostic: it takes callbacks, not URLs. The same browser code supports both models, which is what makes the SDK reusable across Spreedly's integration paths.

Merchant backend calls
DirectPayPal Orders V2 and Vault v3
Spreedly-brokeredSpreedly's paypal_commerce_platform gateway, which calls PayPal server-side

In the brokered model Spreedly creates the PayPal order and returns its id, so the browser half is byte-identical between the two. The demo has a page for each.

7. Technical findings — for discussion

Things we established building against v6 that may be useful to PayPal.

7.1 Vault setup-token key — documentation appears incorrect

For createPayPalSavePaymentSession, the promise passed as session.start()'s second argument must resolve to: 

{ vaultSetupToken: '<id>' }

The published documentation shows { setupToken: <id> }. JS SDK v6.58.x rejects that — and every other shape we tried (bare string, { setupTokenId }, { id }, { token }, passing it in options) — with onError: "no setup token provided", and the approval window opens then immediately closes.

We established this by exhaustively probing every key shape against the live sandbox SDK. Only vaultSetupToken is accepted, and it matches the key onApprove itself reports.

Question: is this a documentation error, or a version-specific change?

7.2 Venmo does not support presentationMode: 'redirect'

ERR_FLOW_UNSUPPORTED_PRESENTATION_MODE — unsupported presentationMode: redirect

Traced to the venmo-payments component bundle. The PayPal sessions accept redirect; Venmo does not.

Question: is full-page redirect support planned for Venmo? Integrations whose payment processor requires a server-visible return leg cannot use a popup, which currently rules Venmo out for them entirely.

7.3 Pay Later requires amount at eligibility

findEligibleMethods filters Pay Later out entirely unless amount is supplied — silently, with no error. The symptom is an eligibility request whose purchase_units[].amount carries currency_code and no value.

Sensible behaviour given financing thresholds are amount-based, but it is easy to miss. Worth making explicit in the docs.

7.5 presentationMode behaviour

For the record, as observed: popup opens a separate browser tab; modal is the in-page overlay; redirect navigates the full page. Worth documenting the distinction — popup and modal are easily assumed to be the same thing.
