# ACH Hosted Fields Integration Guide

`SpreedlyACHFields` collects a US or Canadian bank account in two Spreedly-hosted secure
fields: routing number and account number. The numbers are entered in Spreedly-hosted iframes
and tokenized from inside them, so they never enter your application state — the same
secure-field model as the card number and CVV hosted fields. You lay out the rest of the form
(name, account type) yourself.

For a ready-made form instead, see the [ACH Form Integration Guide](../ach-form/INTEGRATION_GUIDE.md).
To compare the two, see the [ACH overview](../OVERVIEW.md).

## Overview

1. Create a `SpreedlyACHFields` instance and mount the two secure fields (routing +
   account) into container elements you provide.
2. The customer types the numbers into the Spreedly-hosted iframes. Non-sensitive
   fields (name, account type, holder type, bank name) stay as your own inputs.
3. Call `submit(formData)` with only those non-sensitive fields — the SDK tokenizes
   inside the account iframe and emits `tokenGenerated` with `{ message, tokenResponse }` —
   the whole Spreedly transaction, the same shape as card hosted fields.
4. Your backend runs a purchase against an ACH-capable gateway using the token.

```
┌──────────────────────────────┐
│  Merchant page                │
│                               │
│  routing iframe  ◀── Spreedly─hosted, secure
│  account iframe  ◀── Spreedly─hosted, secure (the "brain")
│                               │
│  new SpreedlyACHFields(auth)  │
│  .inAppElements({...})        │      tokenize (routing+account, in-iframe)
│  .submit(formData) ───────────┼───────────────▶ ┌──────────────┐
│                               │                  │ Spreedly Core│
│  on('tokenGenerated',         │ ◀───────────────  └──────┬───────┘
│     { tokenResponse })        │   { token }              │
└───────────────┬───────────────┘                          │ POST /v1/gateways/{gw}/purchase
                │ token                                     ▼
                ▼                                    ┌────────────────┐
         ┌────────────────┐                          │ Merchant       │
         │ Merchant       │ ─────────────────────────│ Backend        │
         │ Backend        │                          └────────────────┘
         └────────────────┘
```

## Prerequisites

- Spreedly account with an [ACH-capable gateway](https://developer.spreedly.com/docs/ach-payments#ach-gateways) configured
- Spreedly environment key and API credentials
- Auth params (nonce, timestamp, signature, certificate_token) generated by your backend

## Step 1: Load the SDK

`SpreedlyACHFields` ships in the Hosted Fields bundle and is exposed as `window.SpreedlyACHFields`.

```html
<script src="https://core.spreedly.com/checkout/sdk/{version}/index.js"></script>
```

> `SpreedlyACHFields` is in the Hosted Fields bundle only. On an Express Checkout page,
> use the prebuilt [`SpreedlyACHForm`](../ach-form/INTEGRATION_GUIDE.md) instead.

## Step 2: Add containers for the two fields

```html
<p>Routing number</p>
<div id="ach-routing"></div>

<p>Account number</p>
<div id="ach-account"></div>
```

Size and style these containers with your own CSS; the SDK renders a borderless
iframe that fills each one. A `<label for>` can't point into an iframe, so use plain text
for the visible label. Each input has its own accessible name ("Bank routing number",
"Bank account number"); change it with `setLabel`.

## Step 3: Create the instance, mount, and listen

```javascript
const ach = new SpreedlyACHFields({
  environment_key: 'your_environment_key',
  certificate_token: 'your_certificate_token',
  nonce: 'generated_nonce',
  timestamp: 'generated_timestamp',
  signature: 'generated_signature',
});

ach.on('ready', () => {
  // Both fields are mounted and connected — safe to customize them now.
  ach.setPlaceholder('routing', 'Routing number');
  ach.setPlaceholder('account', 'Account number');
});

ach.on('tokenGenerated', ({ tokenResponse }) => {
  const token = tokenResponse.payment_method.token;
  // POST `token` to your backend to run the gateway purchase.
});

ach.on('error', (error) => {
  console.error('ACH error:', error);
});

ach.inAppElements({
  routing: { containerId: 'ach-routing' },
  account: { containerId: 'ach-account' },
});
```

Wait for `ready` before calling any other method — it fires once both iframes are
loaded and connected to each other. The account field is masked by default; call
`toggleMask()` to reveal it (e.g. behind a "show" button).

## Step 4: Collect the non-sensitive fields and submit

The customer types the routing and account numbers into the secure fields. Everything
else (name, account type, holder type, bank name) is collected in your own inputs and
passed to `submit`:

```javascript
ach.submit({
  fullName: 'Bob Smith',              // OR firstName + lastName
  bankAccountType: 'checking',        // 'checking' | 'savings'
  bankAccountHolderType: 'personal',  // 'personal' | 'business'
  bankName: 'First Bank of Elbonia',  // optional
});
```

The SDK checks the numbers inside the iframe. The routing number must be 9 digits and pass
the US ABA checksum; a 9-digit number starting with `0` that fails it is sent to Spreedly
to check (it may be Canadian). The account number must be 4–17 digits. On success it emits
`tokenGenerated` with `{ message, tokenResponse }` and securely clears the fields.
Submissions are throttled to one per 2 seconds.

On failure it emits `error`:

| Cause | `error` payload |
| ----- | --------------- |
| Invalid routing or account number | `'Routing number is invalid'` or `'Account number is invalid'`. `validation` fires first with the field state. |
| Submit within 2 seconds of the last one | `'Please wait before submitting again'` |
| Different auth details than the first submit | `'Auth credentials cannot be changed after initial use'` |
| Spreedly rejects the request | Spreedly's error body (for example, a missing name) |

For the keys in Spreedly's error body, see the [Error Keys Reference](../../errors/ERROR_KEYS_REFERENCE.md).

> Any `bankRoutingNumber` / `bankAccountNumber` keys you pass to `submit` are ignored —
> those values come only from the secure fields.

### Account holder name

Send the name one of two ways. Spreedly needs one of them — a bank account with no name is
rejected (`422 "Full name can't be blank"`).

- `fullName` — one field: `ach.submit({ fullName: 'Bob Smith', … })`
- `firstName` + `lastName` — two fields: `ach.submit({ firstName: 'Bob', lastName: 'Smith', … })`

Use whichever matches your form. If you send both, Spreedly receives both. The SDK doesn't
check the name in the browser: a missing name comes back from Spreedly on `error`.

## Step 5: Run the purchase from your backend

After `tokenGenerated` fires, send the token to your backend and run a purchase against
an ACH-capable gateway:

```http
POST https://core.spreedly.com/v1/gateways/{ach_gateway_token}/purchase.json
Authorization: Basic base64(environment_key:access_secret)
Content-Type: application/json

{
  "transaction": {
    "payment_method_token": "...",
    "amount": 1000,
    "currency_code": "USD"
  }
}
```

> **Important:** Run the purchase from your backend, not the browser. Your access
> secret must never be exposed client-side.

## Gating your submit button

`fieldStateChange` reports the state of both fields as the customer types — lengths and
validity only, never the values. Use it to enable your submit button:

```javascript
ach.on('fieldStateChange', ({ validRouting, validAccount }) => {
  submitButton.disabled = !(validRouting && validAccount);
});
```

`validate()` posts a one-off snapshot on the `validation` event with the same shape.

## Styling the fields

Call these after `ready`:

- `setStyles(field, styles)` styles the input text: font, size, color, padding.
- `setPlaceholderStyles(styles)` styles the placeholder text of both fields.
- `setPlaceholder(field, text)` and `setLabel(field, label)` set the placeholder and the
  accessible name.

Web fonts your page loads don't load inside the iframes. Pass a `fontFamily` the browser
already has, or the iframe uses the browser's default font. If you put your own Show button
over the account field, leave room for it with `paddingRight`.

```javascript
ach.on('ready', () => {
  const styles = { fontFamily: 'Helvetica, Arial, sans-serif', fontSize: '16px', color: '#111' };
  ach.setStyles('routing', styles);
  ach.setStyles('account', { ...styles, paddingRight: '64px' });
  ach.setPlaceholderStyles({ color: '#9aa0a6' });
});
```

## Starting over and cleanup

- `resetFields()` clears both fields and securely wipes the held values.
- `reload()` replaces both iframes with new ones in the same containers. Your callbacks stay
  and `ready` fires again; apply your `set*` customizations again in `ready`.
- `destroy()` removes the fields and tears the instance down. Create a new
  `SpreedlyACHFields` to show the fields again.
- `removeHandlers()` removes every `on()` callback. The fields keep working.
- `isLoaded()` tells you whether the fields are mounted.

## Canadian bank accounts

The routing number field takes the 9-digit electronic format: `0`, then the 3-digit
institution number, then the 5-digit transit number. For example, institution `001` and
transit `12345` is `000112345`. Canadian cheques print the transit and institution numbers
separately, so consider telling Canadian customers this format in your page copy or in the
field placeholder (`setPlaceholder('routing', …)`).

## Security notes

- The routing and account numbers are entered in Spreedly-hosted iframes and tokenized
  from inside them. They are never in your page's DOM, your `submit` payload, postMessage
  to your page, logs, or telemetry.
- The account field is masked by default. `fieldStateChange` / `validation` carry only
  lengths and validity.
- The SDK securely clears the held values after a successful tokenization and on
  `resetFields()`. `reload()` and `destroy()` remove the iframes, and the values are
  discarded with them. There is no CVV-style TTL timer for bank data.
- `tokenGenerated` carries Spreedly's transaction, where the bank numbers are already
  masked (`routing_number: "021*"`, `account_number: "*3210"`, plus the `…_display_digits`
  fields). You never get the full numbers.
- The iframes lock to your page's origin on first message (TOFU) and lock the auth
  credentials to their first use.
- ACH data is not PCI-scoped (bank accounts are not cardholder data); this reduces your
  Nacha data-security exposure, the same way card hosted fields reduce PCI scope.
